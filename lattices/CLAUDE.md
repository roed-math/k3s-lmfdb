# Lattice pipeline — agent notes

Context an agent won't get from the code or git history. Current as of 2026-10-22.

## Where the work runs
- **lovelace** (128 physical cores × 2 threads, 2 TB RAM) runs the census; **hensel** (128 cores, 1 TB) is usually busy with someone else's work.
- **mimir** (32 cores, shared with other users' builds) is for development and calibration, not the census. Magma there is 2.30-1 (lovelace and the Mac run 2.29-10). A copy of the listed census is at `/scratch/lattice_data/census32768/`.
- SSH to both is flaky: use script files + `setsid`, and `ssh -o ServerAliveInterval=5`. Don't kill the user's own long-running Magma/sage sessions — only processes you started.
- The census: `run_all.py -r 1 -R 32 -D 32768 -j 96 --skip-enumerate-genera --skip-embeddings ...`. Progress is in `~/census.log` on lovelace; the progress bar uses `\r`, so `tr '\r' '\n' < ~/census.log | grep -oE '[0-9.]+% \([0-9]+/[0-9]+\)' | tail -1`.

## Pipeline shape (what produces a "representative")
- The **listing** stage (`genus.py:create_genus_entry`, calls `genus_symbol.representative()` at ~`genus.py:623`) is where a single lattice is built from a genus symbol and stored as `rep`. This is Sage, and it's a major cost (~per-genus dominated).
- The **fill/enumerate** stages enumerate the *entire* genus (all `h` classes) via Magma's `GenusRepresentativesOrth` (orbit method, `genus_reps.m`), seeded from the stored `rep`. This is NOT single-representative production — don't benchmark Sage `representative()` against Magma `GenusRepresentatives` as if they're the same task.

## Magma gotchas (each cost real debugging time)
- **`Alarm()` is an uncatchable SIGALRM** (exit 142) and never fires inside uninterruptible C builtins (`ShortVectors`, `AutomorphismGroupFaster`, canonical forms, genus enumeration). Bounding those needs the **`TimeoutCall(... : HardKill := true)`** watchdog, in the `Parallel.magma` submodule. Do NOT drop `HardKill` in a refactor — without it a stuck child hangs the parent forever (this looked like ~112-minute fill batches reporting `failed=0`). Until 2026-10-21 the watchdog was forked by the parent, which then waited out its 0.2 s poll on every call (~140 ms per call against ~3 ms), so fill's per-lattice `CanonicalForm`/`AutomorphismGroupFaster`/`ThetaSeries` and connect's per-lattice calls ran *without* it: an overrun was never interrupted, so `--enum-per-lattice-timeout` bounded nothing; the time was spent and the result thrown away. The watchdog now runs from the compute child (~8–13 ms per call; `roed-math/Parallel.magma` branch `fast-hardkill`), and every fill/connect call site passes `HardKill := true`.
- **Polymorphic return = "bad syntax":** a Magma function whose return *type* varies by argument makes any intrinsic that calls it twice fail to compile. See [magma-polymorphic-return].
- **A `TimeoutCall` fork misparses the rest of a script file.** The child's `exit` moves the parent's read position in the file it was given on the command line, so the parent re-reads text at its next 4 KB buffer refill and fails with `bad syntax` (or "Invalid hexadecimal integer") at a nonsensical line and column — or, at top level, can loop re-forking. Any script that forks, including a `tests/test_*.m` suite, must wrap its body in `procedure() ... end procedure();` so Magma parses it all before the first fork; the `run_*.m` drivers already do. This is the "harmless post-success bad syntax" the old `run_tests.m` printed, which was harmless only because that harness `eval`ed each suite from a string.
- **A patched Magma package must be recompiled by the install's owner** (2026-11-04).  If a patch changes a package's signatures, Magma recompiles it on first use and needs to write `<file>.lck`/`.sig` in the install; for anyone else the package then "cannot be loaded".  On lovelace this hit only in `TimeoutCall` children (the parent loaded `neighbors.m` fine), so `check_magma.m` passed while every Magma-enumerated definite genus of the calibration was `enum_fail` in 0.25 s.  `check_magma.m` now uses the packages in a HardKill child first.  Fix: the owner runs Magma on the patched code (or moves the stale `.sig` aside and does).  A `.m` newer than its `.sig` is not by itself a problem: mimir's patched files are too.
- `pkill -f run_fill_genus.m` fails on ~800-char cmdlines (pattern past pkill's match window) — match an early token like `masslimit:=1000`. `pgrep -fc` self-matches; use `ps -eo cmd | grep "[m]asslimit"`.
- **Magma segfaults can report exit code 0 over SSH**, so a batch can silently drop failed labels. `run_fill_genus.sh` (recovered 2026-09-03 from Edgar Costa's fork) wraps `run_fill_genus.m` with `done:=1`: each label prints a `START:`/`DONE:` sentinel pair. Since 2026-10-21 `run_all.py`'s fill stage runs through it (it forwards every `key:=value` guard), and it checks every label in the batch, not just the `START`ed ones: a crash in the batch pre-warm, before any `START`, used to drop the whole batch unreported. After each rank `run_all.py` also lists genera with no `genera_advanced` record in `fill_missing_<rank>.txt` (every guard still writes the genus-level row, so a missing one means an error or crash).

- **Memory is not bounded by any time guard.** On the C=32768 calibration rerun with generous timeouts, rank-17 genera ran Magma processes at 130-220 GB (lovelace is shared). Two causes/fixes (2026-10-22): `CanonicalForm`'s characteristic vector set was capped at 2^20 vectors and doubled -- a rank-17 lattice reached 33250 vectors, a 1.1e9-entry rational matrix -- now `MaxCharVectors` = 4096 and it fails fast past that (same outcome as a timeout); and `--memlimit` (GB, default 32) sets `SetMemoryLimit` in every fill/connect Magma process. Over the cap a `TimeoutCall` child dies and that computation counts as failed; the batch process itself cannot catch it and ends, which `run_fill_genus.sh` reports.

- **Nothing in the fill/connect batch process may run unbounded** (2026-10-22): nothing outside can interrupt it, so one stuck builtin hangs the whole batch.  Every per-lattice computation that can (minimum, kissing number, density, successive minima, root system, Festi-Veniani, IdentifyGroup, Hecke charpoly factorisation, BV hashes, FindLabel's hashing and isometry tests, orthogonal decomposition, the norm <= 2 vectors) runs in a `HardKill` `TimeoutCall` child and is `\N` on an overrun.  Left in the batch process on purpose: LLL, `Dual`, linear algebra, the closed-form `#AutomorphismGroup` of the discriminant group, and `LatticeUniversalityData`/`RepresentsLattice`, which have their own budgets checked at safe points (not HardKill-bounded).
- **A child throws away what Magma initialises lazily**, and the parent's state is what children inherit.  Moving those calls into children made fill ~1.5x slower at rank <= 4 until two fixes: (1) `WarmLatticeCaches` runs each kind of computation once on fixed small lattices in the batch process (SmallGroups data, real constants, factorisation and enumeration setup); (2) `LLL(L)`/`LLL(D)` in the batch process caches a reduced basis that every theta-series child reuses -- the unguarded `Minimum` used to do this as a side effect, and without it each child paid ~4 ms.  With both, 60 rank-4 genera fill in 11.1 s against 11.9 s before the guards.  A HardKill call costs ~2 ms in an idle process and ~7-15 ms in a fill batch, so group cheap calls into one child.
- **The batch orth pre-warm is off by default (`--warm-limit 0`, 2026-10-22).** It runs in the batch's own Magma process (so the per-genus forks inherit the warmed cache), so nothing can kill it, and its `SetGenusOrthTimeBudget` deadline is only checked at safe points in the orth code. On the C=32768 calibration, with a warm `orth_cache/` from the rank above, a rank-8 batch spent 25 h at 100% CPU in it and never finished its first genus (`8.8.129.101`, which fills in ~110 s from cold on mimir). A bounded version would run it in a HardKill child that returns its cache entries; not done.

## Coverage / data-integrity facts
- **Label order** (`cmp_lat`, 2026-10-22): aut group order, minimum, root system, theta series, dual theta series, Gram matrix.  David's decision: keep the invariants as sort keys and accept that labels are fixed by the run that enumerates the genus (a timed-out key, or a Gram matrix that is canonical only when `CanonicalForm` finished, can order a genus differently on another run); a missing key sorts after every present one so the order is a total preorder (comparing only when both are present was not transitive).  Indefinite rank >= 3 labels follow the spinor-genus rule David agreed to: class `.1` is the class of the published `rep`, `.k` the class at spinor vector e from it with k-1 = e in binary over the greedy smallest-prime basis -- still a choice of base point, so not canonical.  `genus_reps_Spinor` builds them in that order itself (same classes and order as Magma's `SpinorGenera`, checked with Oscar; the lattices can differ, since `Neighbors` returns a state-dependent first neighbour), and fill records `spinor_generators` (genera_advanced) and `spinor_coordinates` (lat_basic).  Because the labels hang on `rep`, compare any regenerated genera_basic with the published one using `check_spinor_base.py` before trusting its labels.
- **`root_sublattice` is a fill (`lat_basic.format`) column**: the root system of the norm <= 2 vectors, canonical string `"I4 A2 2E8"` (I, A, D, E, rank increasing, multiplicity prefixes), `"0"` for none.  Not `""`: Magma's `Split` drops empty fields, and connect/tensor read basic records with `Split`, so an empty field misaligns the whole record.  `root_complement` stays in connect (it needs `FindLabel`).
- Overrunning a genus's `enum-timelimit` **discards ALL its lattices** (`fill_genus.m`, `lats := []`), by design — a partial set would contradict the stored `class_number`. So `enum-timelimit` is a coverage switch, not a speed knob; calibrated to 900s at C=256.
- `--enum-per-lattice-timeout` is a **per-operation** cap (canonical form, aut group, primal+dual theta each independently), so ~4× per lattice; the aggregate guard is the per-genus `--enum-timelimit`, not that option.
- A dropped/timed-out genus is a **MISSING `genera_advanced` file**, not a `\N` — null-scanning cannot see it. Audit timeouts vs crashes accordingly. See [lattice-pipeline-coverage-diagnostics].
- Mass is a terrible work proxy: high-rank genera have huge Aut → tiny mass despite large `h`. `run_all.py` uses a work-aware batch metric (`genus_work`, `--batch-work-target`) instead.
- **CI exists as of 2026-09-03, but is gated off.** There was none before (zero workflows/runs here or on `jvoight/k3s-lmfdb`, nothing running `lattices/tests/`), which is why the bugs below — and the `fill_genus.m`/`hanke_full.py` ones above — sat unnoticed. `.github/workflows/tests.yml` now runs one job per `lattices/tests/test_*.m` suite via `tests/run.sh`, using the convention from `assaferan/AtkinLehnerQuotients`. Push/PR runs skip the slow suites; they run on `workflow_dispatch` and a weekly Sunday cron instead. The workflow parses `SLOW_SUITES` out of `tests/run.sh` rather than keeping its own copy, so the two cannot drift. **It skips cleanly (does not fail) until `MAGMA_URL`/`MAGMA_USERNAME`/`MAGMA_PASSWORD` secrets are set on the repo** — they are not, so nothing actually executes on GitHub yet; run `tests/run.sh` locally from `lattices/` in the meantime. Note `test_l12a_plus` takes ~2h23m and `test_brandhorst` ~4m (both `CanonicalForm`-bound); the other eight total ~18s and `test_universality` (from #73) ~75s, so `run.sh` excludes the first two unless `--slow` is passed. The bare `assert`s in the old suites could exit 0 on failure (no `SetQuitOnError`); `tests/assertions.m` sets it, so that class of false green is gone.
- **Upload files: `make_upload.py` (2026-11-03).**  `nde_to_upload.sage` is not the pipeline's upload path: it reads a different program's output (`data/nde_out/`, "enumerated by Noam's code"), writes K3-family tables from variables it never defines, and only its `load_schemas()` was ever used.  `make_upload.py` joins the flat files per label into `lat_genera`/`lat_lattices` reload files (schema column order, through that same `load_schemas()`) and checks every value against its column type; run it before any upload.  First run on the R=4, D=120 smoke: `tensor_decompositions` (jsonb) held unquoted labels, not JSON (fixed in `run_tensor.m`); `deep_holes` (`numeric[]`) holds exact fractions like `{{-1/2}}`, which Postgres rejects -- needs a schema decision (text[], jsonb, or integer numerators over a common denominator), open.  Watch `class_number` (smallint, max 32767) if `--enum-masslimit` goes up.
- **`schemas/*.md` is not just documentation** — `nde_to_upload.sage`'s `load_schemas()` parses it as the machine-readable schema (`record.get(col)` per row), so a bad column name silently uploads nulls instead of erroring. Fixed 2026-09-03: `load_schemas()` itself could not run at all (three separate crashes — `set()` missing before `.issubset`, `hash()` on an unhashable list, a missing arg to `save_schema_hashes`), and once fixed it exposed five columns in `lat_lattices.md` that would have nulled out silently (a 2-pipe row the parser drops, a duplicated `theta_prec` masking `dual_theta_prec`, `covering_norm` vs the actual `covering_norm_num`/`_den` fields, stray brackets on `[canonical_gram]`, and the markdown header row itself being parsed as a data column named `Column`). `lattices/tests/test_schema_consistency.py` now checks this — drives the real `load_schemas()`, not a hand copy, since an earlier draft of the check mirrored the parser by hand and the copy was more correct than the original, which is exactly what hid the header-row bug.

- **Calibration:** `--fill-stats` makes `FillGenus` write a `fill_stats/` record per genus (outcome or the guard that decided it, class number, per-phase wall-clock, slowest single lattice; `fill_stats.format`). `calibrate_fill.py` samples the census by (rank, nminus, log2 det), runs fill on the sample and reports cost and coverage extrapolated to the census. See README "Calibrating the fill stage".
- **Indefinite lattices have no per-lattice hash** (`\N`), so `FindLabel` resolved none of them (every indefinite `dual_label` was `\N`, I_{3,1} included). Fixed 2026-10-21: class number 1 by the single stored row, rank 2 by an exact isometry test (`IsIsometricBinary` in `genus_reps.m`). Rank >= 3 genera with several classes: Magma cannot tell their classes apart (its spinor-genus `eq` falls back to isometry tests, which need a definite form), so `FindLabel` returns null plus the genus.  Since 2026-11-03 it does the same when hashing or the definite isometry test overruns (returning "genus;candidate labels" for the latter), connect records every such lookup in `label_lookups/<rank>/<nplus>/<source label>` (`column|genus|gram|candidates`, empty = every class), and after connect the Oscar pool's `resolve` task (`LMFDBLattices/src/resolve.jl`; it replaced `oscar/resolve_indefinite.jl`) finds the class with `is_isometric` and patches the advanced record; no match or several is an error record.  This covers `dual_label`, `primitive_scaling`, `even_sublattice`, `norm1_complement` and `root_complement`; lookups for orthogonal factors (a sorted list with multiplicities and a name, not one column) and from `tensor.m` and `name_lattices.m` stay null. connect builds the rescaled dual of an indefinite lattice from the inverse Gram matrix instead of calling `Dual`, which was reported to need a definite form on 2.29 (2.30-1 copes; on all 722 indefinite smoke lattices the two agree in det, genus and label).
- **Indefinite class numbers (resolved 2026-11-03; the Magma patch is required but not yet applied to any install).**  Rank >= 3: the classes are the improper spinor genera (Eichler), and `genus_reps_Spinor` builds one per element of the spinor group from Magma's spinor characters (`spinor_generators` in `genus_reps.m`, odd primes only: Magma's `SpinorGenerators` can start with 2, where an odd lattice may have no 2-neighbours).  Stock Magma (2.29-10, 2.30-1) gets these wrong through three bugs in `package/Lattice/Lat/diagonal.m`, fixed by `magma_patches/diagonal-2.30-1.patch` (three fixes; see `magma_patches/README.md`; `check_magma.m` requires it via `MagmaSpinorPatched`); and Hecke had one (Hecke.jl PR #2611, `_automorphous_numbers`; not in the pinned Hecke 0.39.21: without it Oscar's indefinite `spinor_genera_in_genus` and `is_isometric` are wrong in the affected genera -- 13 of the 19162 sample genera get 1 class instead of 2 -- so `LMFDBLattices` applies the PR at load time, see "Oscar in the pipeline").  With all four fixes Magma and Hecke agree on all 19162 class numbers of the 2026-10-22 sample (ranks 3-5, square factors in det) and on the spinor character values in all 39 multi-class genera; explicit isometries (`/scratch/claudeF/work/spinor_disputed.tsv`, `.../spinor_fix/`) are consistent with every count.  Without the complement patch, Magma's count is right but its character is wrong in 13 genera, so the pipeline stores the rep and an isometric neighbour as two classes (proved isometric in 3.2.10800.0001.11.01.293b and .493b).  Every multi-class indefinite rank >= 3 genus filled with unpatched Magma is suspect.  Rank 4-5 samples had no multi-class genera at all.  Rank 2 non-square discriminant: see the Magma patch below. Square discriminants (`genus_reps_square_disc`) and definite binary genera were already right.
- **Magma's `Mass` is wrong in ranks 2 mod 4 (found 2026-11-03 by the lovelace benchmark).**  `DedekindZetaExact` (`package/Lattice/Lat/mass.m`) evaluates L(chi_d, 1-n) numerically when n is odd and recognises it with `BestApproximation`: 14.14.2127.9 (same genus as I_13 + <2127>) is off by a relative 1e-30, and in a scan of 183 discriminants the value is wrong or errors for 14% at rank 14/18, 67% at 22, 89-95% at 26/30.  The orbit method (`tally eq gmass`) and the neighbour walk (`while mass_left gt 0`) stop on Magma's `Mass`, so such genera enumerate wrongly or fail.  Fixed by `magma_patches/mass-2.30-1.patch` (-B_{k,chi}/k; note `AbsoluteDiscriminant` drops the sign), tested on a copy of the package via `MAGMA_SYSTEM_SPEC` (agrees with Sage on all 545 benchmark definite genera); `check_magma.m` requires it (`MagmaMassPatched`).  Not yet applied to mimir's or lovelace's install; bug report text in `magma_patches/mass-2.30-1-report.md`.
- **The census needs a patched Magma (2026-10-22).** Magma's `GenusRepresentatives` on indefinite binary lattices (`BinaryGenusRepresentatives` in `package/Lattice/Lat/neighbors.m`) works in `ClassGroup(QuadraticForms(D))`, which for D > 0 is the class group in the wide sense.  When the fundamental unit has norm +1, each wide class lifts to two proper classes, and the code can return a lattice from another genus (x^2 - 79y^2: 3 lattices, one outside the genus, in about 49 calls in 50; the genus has 2 classes) or miss a class (x^2 - 34y^2 with `Proper`: 1 of 2).  It also does not identify a class with its mirror image (x^2 - 37y^2: 3 instead of 2).  Over the 1744 genera with |det| <= 400 it was wrong in 109, checked against Sage.  `SpinorRepresentatives` has the same bug.  The fix is `magma_patches/neighbors-2.30-1.patch`: proper classes from `ReducedForms`, genus g*C^2, spinor genus g*C^4, canonical cycle representatives.  It was applied to mimir's 2.30-1 and reported to Magma on 2026-10-22.  `run_all.py` runs `check_magma.m` before the fill stage and stops if it fails (`--allow-unpatched-magma` overrides); lovelace's 2.29-10 needs the patch too, possibly ported by hand.  The patch also makes `Neighbours` work on indefinite lattices: it rejected every indefinite binary lattice, and every one of rank >= 3 with content > 1, because it rescales with `LatticeWithGram` without `CheckPositive := false`.  So `SpinorGenera` failed on such genera, which never filled before 2026-10-22; `genus_reps_Spinor` now divides out the content itself, so the pipeline does not depend on that part of the patch.  An earlier note here, and a commit (5980826), read this as Magma returning mirror pairs, and that commit's isometry dedup in `genus_reps_Magma` is now a no-op.
- **Embedding stage is chunked and resumable** (`--embed-chunk`, default 200 domain genera per job): each job commits atomically to `inclusions/data/<task>_<list>.c<k>/` with the sha1 of its inputs, reruns without `--clean` skip committed jobs, and a chunk that times out only caps the completeness certificate below its smallest det (`embed_labels/expected_jobs.txt`, `derive_certificates`). Before, one job per rank pair meant one timeout lost a whole pair: at R=4, D=120 under load ~225 the rank-2 -> 3 corank-1 job hit the 3600 s limit. Two things learned making it: (1) the vendored overlattice routine looks overlattices up in its own genus list, so a chunk must carry the whole rank as a lookup pool (`_prime_index_overlattices_pool` in `driver.jl`) -- without it 983 of 32710 rows vanished silently; (2) each job had a fixed cost of ~270 s on a loaded machine (Julia/Oscar startup and compilation, pool loading, per-chunk codomain setup), so chunks of 25 cost 3.8x the unchunked total job time.  Since 2026-11-03 the jobs run on the Oscar worker pool (task `embed`, code in `LMFDBLattices/src/embed.jl`, which holds the vendored routines with the pipeline's changes applied in place -- a package may not overwrite methods while precompiling, so the driver's include-then-override no longer works), so startup is paid once per worker and the corank-1/overlattice compilation is cached by the precompile workload; per-chunk pool loading remains.

- **`adjacency_matrix` is stored in label order since 2026-10-22**; before, it was in Magma's enumeration order, which is random per run (the same code gave different matrices for different genera on consecutive smoke runs), so rows could not be matched to labels.  `pneighbors` was right all along: `Sort(~S, f, ~p)` gives new `S[i]` = old `S[i^p]`.
- `tests/test_genus_reps_orth.m` used to fail in any checkout where a pipeline run had filled `orth_cache/` (the cached representative comes back in another basis); it now compares up to isometry.

## Theta series: deciding equality (2026-11-04)
- **`is_theta_distinguished` is decided in two places.**  Fill (`SetHashes`): differing early, or agreeing to `ThetaSturmPrecision` (extended when `theta_vector_estimate` says it is cheap).  The rest goes to the theta-Hecke pass (`theta_hecke.m`, `run_theta_hecke.m`, `run_all.py` after fill), which needs no more coefficients: the relations among a genus's theta series are stable under the p-neighbour adjacency matrix, and what survives lies in Hecke eigenspaces of the cusp space that few coefficients determine.  David asked for this ("you can usually distinguish modular forms with much smaller precision"); the Sturm bound is far too big at rank >= 6 with large level.
- **Eichler's relation, as Magma computes adjacency:** `AdjacencyMatrix(G, p)[j, i]` = number of p-neighbours of class i isometric to class j (source in the *column*), and sum_j A[j,i] theta_j = (T(p^2) + p + ... + p^(n-3)) theta_i.  Fitted, then checked (`EichlerRelationHolds`, `tests/test_theta_hecke.m`) on ranks 2-9: odd and even lattices, chi(p) = +-1, half-integral weight, p = 2.  Work with g = sum q^((v,v)/2) for even lattices (level of A; p = 2 is a good prime when that level is odd) and with the pipeline's f = sum q^(v,v) for odd ones (level of 2A).  Characters: ((-1)^k det S / .) in weight k, (2 det S / .) in weight n/2 odd (Magma's `HalfIntegralWeightForms` convention), S the even Gram matrix.  Magma's `HeckeOperator` matrices act on row vectors of `Basis` coordinates.
- Cost is in building the cusp space (modular symbols: 1-20 s at weight <= 4, level <= 3000; 58 s at weight 6 level 1000; 285 s at weight 8 level 600 on mimir), so the pass builds each space once for all its genera and caches per-factor eigenspace data in `theta_hecke_spaces/`.  The adjacency matrix costs ~h p^(n-2) isometry identifications; fill's stored matrices are reused when they are at the pass's prime.
- Magma gotchas hit here: `adj` and `diff` cannot be identifiers (reserved), braces anywhere in an intrinsic docstring are a syntax error, `Write`/`Sprintf` wrap long lines unless `SetColumns(0)` (fill sets it, tests do not), and `Split` drops a leading empty field, so splitting an absolute path on "/" makes it relative.

## Oscar in the pipeline (2026-11-03)
- **Genus enumeration moved to Oscar for indefinite rank >= 3 and definite rank <= 8** (David's decision after the benchmark).  `oscar/pool.jl --task enumerate` runs before fill on a Distributed.jl pool and writes `oscar_genus/` records; `FillGenus` takes the classes from an `ok` record, cross-checks Oscar's #Aut and root system against Magma's (a mismatch is an error, so the genus fails visibly) and uses Oscar's when Magma's overran.  A failed Oscar record falls back to Magma for definite genera but not for indefinite rank >= 3 (Magma may overcount).  Indefinite classes come from Hecke's `spinor_genera_in_genus(rep)`, whose order is the agreed label rule (class 1 = rep, binary in the greedy smallest-prime basis of `improper_spinor_generators`; 2 is always a bad prime there).  R=4, D=120 smoke: identical class numbers, aut orders and masses (Oscar's mass vs Sage's stored one) on all 1130 Oscar genera, and identical pipeline output except `aut_group` *generators* in 29 lattices (same groups; Magma's generator choice varies with process state).
- **`LMFDBLattices` patches Hecke at load time** (`src/hecke_fixes.jl`, from `__init__`, so in the master and every pool worker; 2026-11-03): Hecke.jl PR #2611 (`_automorphous_numbers`), which the pinned Hecke 0.39.21 lacks.  It rewrites the two functions from the installed Hecke's own source text and evaluates them into Hecke (method overwriting is not allowed while the package precompiles); it is a no-op once the source has the fix and an error if the source matches neither form.  `LMFDBLattices.HECKE_PR2611[]` says which.  With it the enumerate stage gives the patched Magma's classes and generators on all 17 formerly disputed genera, label by label; tested by `oscar/test_hecke_fixes.jl`.  Remove it once the Oscar pin includes the PR.
- **The warm-up is compilation, not loading.** Fresh process at load ~160: `using Oscar` 31 s, then the first definite `representatives` 110 s, `is_isometric` 7 s, `mass` 5 s.  The package `oscar/LMFDBLattices` with a PrecompileTools workload caches that code (first `representatives` 0.9 s on lattices the workload never saw).  Any edit to the package triggers ~5 min of precompilation at the next load.  Stage code that only runs in Oscar belongs in the package, not in a script.
- Mass stays with Magma for the genera Magma enumerates: 0.15-0.3 s per call at ranks 9-12 (benchmark), well under 1% of a fill at those ranks.  Aut orders and root systems too: both systems succeed on all benchmark cases and Magma is faster from rank 12.  Isometry tests are where Oscar matters in connect (Magma's `IsIsometric` failed on 9-18 of ~34 cases per rank at ranks 10-16, Oscar on none).
- **Distributed gotcha: never `isready` a `remotecall` Future to poll a busy worker.**  The result lives on the worker, so `isready` is a request to it, and a single-threaded worker inside a long Oscar/GAP/flint call that never yields cannot answer until the call returns.  The pool's timeout check sat behind that call: on the first calibration test (2026-11-03) a batch hung 47 min past its 600 s limit and the whole stage waited.  The pool now runs `remotecall_fetch` in a local task and polls `istaskdone`, and `oscar/test_pool.jl` has a `csleep` case (a C `sleep`, which does not yield) that must time out.  Also: Julia buffers stdout to a file, so the pool flushes its log lines; `addprocs` gives up on a worker that takes longer than `JULIA_WORKER_TIMEOUT` (60 s by default; workers took ~100 s under load ~200), so the pool sets it to 900 s and retries; and `rmprocs` waits forever for a busy worker, so the pool kills leftover workers at the end.
- **Distributed gotcha**: load the package (and Oscar) in the master *before* `addprocs`; with a dev checkout of Oscar, its `__init__` shells out to `git`, which deadlocks once addprocs has installed its SIGCHLD handling.

## Magma vs Oscar benchmark (`benchmark/`, 2026-10-22)
- `bench.py sample|run|report` (README "Benchmarking Magma against Oscar"); the Magma and Oscar calls are in `bench_magma.m` / `bench_oscar.jl`, Oscar's pipeline-format values in `oscar/invariants.jl`.  Meant to run on lovelace; mimir was only used to test it.
- **Magma returns the identical lattice object for an equal Gram matrix** (`LatticeWithGram`, `LatticeWithBasis`, `Lattice` alike) while any reference to the first one is alive, so its cached minimum, short vectors etc. come along; once every reference is gone (`delete`) the next one is fresh.  A benchmark that repeats a call on one Gram matrix measures that cache.  bench gives every call in a job its own Gram matrix U G U^t (`scramble`, the same in both servers).
- Magma's `Realtime()` and `Cputime()` advance in 10 ms steps (2.30-1 on mimir), so fast calls are timed in blocks.  **`Cputime()` stays at 0 in a `TimeoutCall` child** (2.30-1: 0.000 against 0.73 s from `/proc/self/stat` for the same loop); bench reads `/proc/self/stat` instead.  Magma's `ThetaSeries` does not enumerate vectors one by one: E8 to norm 40 (11.5 million vectors) takes < 50 ms, which no enumeration does.
- The TimeoutCall fork gotcha above also hits a regular file on **stdin**: a server reading jobs from `< file` re-reads them in a loop.  Feed it through a pipe.
- **`festi_veniani_index` was wrong until 2026-11-03 and is now computed by Oscar.**  It must be [O(q_L) : im O(L)] (Festi-Veniani; David confirmed), but fill divided #Aut(L#/L) of the abelian group by the image, a different number whenever O(q_L) is smaller (3.3.62.6: 30 vs 2; A1+A1: 3 vs 1).  Magma has no O(q) for torsion forms, so fill now records the image order in `festi_veniani/<rank>/<nplus>/<genus>` (`label|image order`) and leaves the column `\N`; `oscar/fix_festi_veniani.jl` (run by `run_all.py` after fill, `--fv-*`) computes |O(q_L)| from the genus rep and writes the index.  `--legacy` converts older data: |image| = #Aut(L#/L) / stored value (`abelian_aut_order`, Hillar-Rhea; agrees with Magma's `#AutomorphismGroup` on 545 benchmark discriminant groups), saved to the sidecar before patching, so reruns change nothing.  Validated: on the smoke tree (894 definite lattices) both the converted legacy values and a fresh fill + pass agree with Oscar's `image_in_Oq` index computed on the stored Gram; tests in `oscar/test_fix_festi_veniani.jl`.  |O(q_L)| is cheap (bench task `oq_order`, 2026-11-03): the 107 hardest definite discriminant forms in the census (2-rank up to 11, mixed 2- and 3-parts, many 2-power scales) took at most 0.44 s per call on mimir at load ~160 (median 0.07 s).  The 6 Oscar `disc_image` timeouts on lovelace were odd indefinite lattices of rank 14-16, where `image_in_Oq` computes the image of O(L) by strong approximation (one had |O(q)| = 720), not O(q) -- that is where extending the index to indefinite lattices would get expensive.  Distinct `conway_symbol` local parts are ~73% of definite genera, so caching |O(q_L)| per form saves little.  The LMFDB knowl `lattice.festi_veniani_index` (in the database, not this repo) may still describe the old definition.
- **`AutomorphismGroupFaster` (aut_char.mag) is very slow on unreduced bases**: E8+E8 in bases with entries up to ~100 took over 60 s in 9 of 10 cases, against 0.07 s after `LLLGram` (stock `AutomorphismGroup`: 0.02 s either way).  Fill passes it a reduced (canonical/LLL) Gram, but the orbit method calls it on `glue_parent`'s P, whose Gram comes from a Hermite-form basis (`genus_reps.m` ~385, used at ~430) -- untested whether those bases are bad enough to matter.  bench's Magma default variant LLL-reduces first, as fill does.
- **Stock `OrthogonalDecomposition` can exhaust memory**: on 16.16.41.0 (E8 + a rank-8 det-41 summand) it passed 12 GB on both the stored and the LLL-reduced Gram, where `OrthogonalDecompositionFaster` answers instantly; on direct sums of root lattices stock is 1.5-13x faster.  Stock `GenusRepresentatives` refuses some rank 14-16 genera ("Requires computation of orbits of 5^14 points").
- **The stock intrinsics blow up on decomposable lattices with a summand of large determinant** (e.g. Z^4 + a rank-4 det-429 block; Sage's `representative()` often produces such reps).  bench pilot on census reps, definite ranks 6-16 (2026-10-23, mimir, 120 s limit): stock `AutomorphismGroup` timed out on 8 of ~60 and took 1-67 s on ~10 more where `AutomorphismGroupFaster` took <= 0.25 s; stock `OrthogonalDecomposition` crashed (memory) or timed out on 6 and was 10-20000x slower on ~25 (Faster <= 0.02 s everywhere); stock `IsIsometric` (what connect's `FindLabel` uses) timed out on 10, the same lattices; Magma's `SuccessiveMinima` (fill) crashed or timed out on 4 of them.  `AutomorphismGroupFaster` is up to ~17x slower on some indecomposable lattices but stayed <= 0.25 s.  So keep the Faster versions.  Oscar handles these lattices: `isometry_group`, `irreducible_components` and `is_isometric` take 0.001-0.26 s on all 11 such pilot lattices; successive minima are hard for both (Oscar ran out of 16 GB on 7).
- **Pilot findings for running bench (2026-10-23, `/scratch/claudeF/work/bench/pilot_results/`):** 0 value mismatches over 150 census cases (ranks 6-16, both kinds, all variants).  Hard failures come in (task, rank) groups and the skip rule caps them at 2 per group: Magma's in class_number (both variants), stock aut/orth, `IsIsometric` and successive minima at every definite rank; Oscar's in class_number (all three variants, every definite rank), successive minima, and `disc_image` for indefinite rank 14-16.  **Each Oscar failure restarts its server, and the warm-up took 9-10 min under mimir's load ~150 (2.5 min at load ~30)**: 56 Oscar starts were most of its ~11 server-hours.  No value disagreements between stock Magma, the pipeline's versions and Oscar in any aut order or decomposition so far (structured sums, Leech, K12, census ranks 2-16).
