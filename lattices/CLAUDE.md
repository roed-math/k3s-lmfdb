# Lattice pipeline — agent notes

Context an agent won't get from the code or git history. Current as of 2026-07-17.

## Where the work runs
- **lovelace** (128 physical cores × 2 threads, 2 TB RAM) runs the census; **hensel** (128 cores, 1 TB) is usually busy with someone else's work.
- SSH to both is flaky: use script files + `setsid`, and `ssh -o ServerAliveInterval=5`. Don't kill the user's own long-running Magma/sage sessions — only processes you started.
- The census: `run_all.py -r 1 -R 32 -D 32768 -j 96 --skip-enumerate-genera --skip-embeddings ...`. Progress is in `~/census.log` on lovelace; the progress bar uses `\r`, so `tr '\r' '\n' < ~/census.log | grep -oE '[0-9.]+% \([0-9]+/[0-9]+\)' | tail -1`.

## Pipeline shape (what produces a "representative")
- The **listing** stage (`genus.py:create_genus_entry`, calls `genus_symbol.representative()` at ~`genus.py:623`) is where a single lattice is built from a genus symbol and stored as `rep`. This is Sage, and it's a major cost (~per-genus dominated).
- The **fill/enumerate** stages enumerate the *entire* genus (all `h` classes) via Magma's `GenusRepresentativesOrth` (orbit method, `genus_reps.m`), seeded from the stored `rep`. This is NOT single-representative production — don't benchmark Sage `representative()` against Magma `GenusRepresentatives` as if they're the same task.

## Magma gotchas (each cost real debugging time)
- **`Alarm()` is an uncatchable SIGALRM** (exit 142) and never fires inside uninterruptible C builtins (`ShortVectors`, `AutomorphismGroupFaster`, canonical forms, genus enumeration). Bounding those needs the **`TimeoutCall(... : HardKill := true)`** watchdog (forks a second child that SIGKILLs the compute child). It's in the `Parallel.magma` submodule. Do NOT drop `HardKill` in a refactor — without it a stuck child hangs the parent forever (this looked like ~112-minute fill batches reporting `failed=0`).
- **Polymorphic return = "bad syntax":** a Magma function whose return *type* varies by argument makes any intrinsic that calls it twice fail to compile. See [magma-polymorphic-return].
- `pkill -f run_fill_genus.m` fails on ~800-char cmdlines (pattern past pkill's match window) — match an early token like `masslimit:=1000`. `pgrep -fc` self-matches; use `ps -eo cmd | grep "[m]asslimit"`.
- **Magma segfaults can report exit code 0 over SSH**, so a batch can silently drop failed labels. `run_fill_genus.sh` (recovered 2026-09-03 from Edgar Costa's fork, which had drifted 7 commits ahead of upstream unmerged) wraps `run_fill_genus.m` with `done:=1`: each label prints a `START:`/`DONE:` sentinel pair, and the wrapper reports any label that got a `START` but never a matching `DONE`/`ERROR` as a segfault. `run_fill_genus.m` also now runs with `SetQuitOnError(true)`. Verified: real `FillGenus` run via the wrapper on 3 labels (exit 0, correct output), and the sentinel-diff logic tested directly against a synthetic crash case.

## Coverage / data-integrity facts
- Overrunning a genus's `enum-timelimit` **discards ALL its lattices** (`fill_genus.m`, `lats := []`), by design — a partial set would contradict the stored `class_number`. So `enum-timelimit` is a coverage switch, not a speed knob; calibrated to 900s at C=256.
- `--enum-per-lattice-timeout` is a **per-operation** cap (canonical form, aut group, primal+dual theta each independently), so ~4× per lattice; the aggregate guard is the per-genus `--enum-timelimit`, not that option.
- A dropped/timed-out genus is a **MISSING `genera_advanced` file**, not a `\N` — null-scanning cannot see it. Audit timeouts vs crashes accordingly. See [lattice-pipeline-coverage-diagnostics].
- Mass is a terrible work proxy: high-rank genera have huge Aut → tiny mass despite large `h`. `run_all.py` uses a work-aware batch metric (`genus_work`, `--batch-work-target`) instead.
- **CI exists as of 2026-09-03, but is gated off.** There was none before (zero workflows/runs here or on `jvoight/k3s-lmfdb`, nothing running `lattices/tests/`), which is why the bugs below — and the `fill_genus.m`/`hanke_full.py` ones above — sat unnoticed. `.github/workflows/tests.yml` now runs one job per `lattices/tests/test_*.m` suite via `tests/run.sh`, using the convention from `assaferan/AtkinLehnerQuotients`. Push/PR runs skip the slow suites; they run on `workflow_dispatch` and a weekly Sunday cron instead. The workflow parses `SLOW_SUITES` out of `tests/run.sh` rather than keeping its own copy, so the two cannot drift. **It skips cleanly (does not fail) until `MAGMA_URL`/`MAGMA_USERNAME`/`MAGMA_PASSWORD` secrets are set on the repo** — they are not, so nothing actually executes on GitHub yet; run `tests/run.sh` locally from `lattices/` in the meantime. Note `test_l12a_plus` takes ~2h23m and `test_brandhorst` ~4m (both `CanonicalForm`-bound); the other eight total ~18s, so `run.sh` excludes those two unless `--slow` is passed. The bare `assert`s in the old suites could exit 0 on failure (no `SetQuitOnError`); `tests/assertions.m` sets it, so that class of false green is gone.
- **`schemas/*.md` is not just documentation** — `nde_to_upload.sage`'s `load_schemas()` parses it as the machine-readable schema (`record.get(col)` per row), so a bad column name silently uploads nulls instead of erroring. Fixed 2026-09-03: `load_schemas()` itself could not run at all (three separate crashes — `set()` missing before `.issubset`, `hash()` on an unhashable list, a missing arg to `save_schema_hashes`), and once fixed it exposed five columns in `lat_lattices.md` that would have nulled out silently (a 2-pipe row the parser drops, a duplicated `theta_prec` masking `dual_theta_prec`, `covering_norm` vs the actual `covering_norm_num`/`_den` fields, stray brackets on `[canonical_gram]`, and the markdown header row itself being parsed as a data column named `Column`). `lattices/tests/test_schema_consistency.py` now checks this — drives the real `load_schemas()`, not a hand copy, since an earlier draft of the check mirrored the parser by hand and the copy was more correct than the original, which is exactly what hid the header-row bug.

## Open follow-ups
- **`fill_genus.m` aut/gram basis mismatch — fixed 2026-09-03:** on a `CanonicalForm` timeout, the stored gram was in the LLL basis (`:345`) but `aut_group` was computed in `gram0`'s basis (`Lcanon := L` at `:354`). Confirmed concretely on a scrambled-basis E8 test case: ALL of the computed group's generators failed to preserve the stored gram (0/4 preserved it before the fix, 4/4 after). Fixed by starting `Lcanon` from `LatticeWithGram(gram)` (matching `lat["gram"]`'s basis from the outset) instead of `L`; `CanonicalForm` succeeding still overwrites both together as before. Verified end-to-end: `FillGenus` run for real on 69 rank-3 genera (88 lattices), every one going through the previously-buggy non-canonical path, zero `aut_group`/gram mismatches. connect's consumers (Voronoi, shortest, t-design) are covered by this; the PR #73 `RepresentsLattice` orbit-collapse consumer this note originally mentioned was never independently located (see the unresolved PR #73 reference below) so it wasn't specifically re-verified, but the fix addresses the general hazard regardless of which consumer hits it. See [fill-genus-aut-gram-basis-mismatch].
- **`hanke_full.py`** `maximal_overlattice_2` — **wired into the listing stage as of 2026-09-03** (`genus.py:write_all_of_sig_between_genera_basic` calls `install_fast_maximal_overlattice()`). Wiring it in immediately surfaced a real bug the small-prime and large-prime sweeps both missed: `p_neighbor_lattice` (used by `finish()`'s odd-but-not-already-even 2-adic branch) returned a lattice with a fresh, disconnected ambient embedding instead of one composed with the input's `basis_matrix()` (contrast `even_sublattice` a few lines above, which does this correctly) — invisible to any check that only compares Gram matrices / abstract `Genus()`, but fatal to `local_modification`, which combines lattices via real ambient coordinates. Fixed by embedding the neighbour in the same ambient space as its input. Measured 1.91× on `representative()` over 1399 genus symbols (232s → 121s); also verified against Sage's own internal `Genus(L) == self` check across 3456 genus symbols (ranks 1-12, three indefinite signatures, det ≤ 50). See `lattices/tests/test_hanke_large_primes.py` for the large-prime/high-rank regression sweep this relies on — note it only exercises the `p=None` path, not `p=<prime>`, so it would NOT have caught the `p_neighbor_lattice` bug on its own; that needed the end-to-end pipeline run.
